Principles

Two ideas shape every skill here. Knowing them makes the rest of the page predictable.

Test-driven development

Test-driven development, TDD for short, means you write the test before the code it tests. The test fails at first, because the code doesn't exist yet. Then you write code until it passes, then you tidy up. The loop is called red, green, refactor. Red and green are the colours a test runner shows for failing and passing tests.

Red. architect-issue writes the tests and checks that every one fails for the right reason. Done is now decided, before any real code exists.

Green. implement-issue writes code until those tests pass. It may not edit the tests, so it can't make the work easier by lowering the bar.

Refactor. refactor-issue improves the code's shape without changing what it does. The tests prove nothing broke.

Textbook TDD goes around this loop every few minutes, one test at a time. We go around once per issue, with all its tests at once, and each step is its own skill and its own commit. It's slower per lap, but each commit is a clean checkpoint you can review on its own.

Who decides what

Decisions belong to people. Typing belongs to Claude. The skills that settle what to build and what the code looks like from outside need you in the chat. The two that only carry out a settled plan run on their own.

implement-issue and refactor-issue don't ask for permission, but they don't guess either. They come back to you when:
  • a test contradicts the issue, or a stub can't do what its docstring promises
  • the same test fails the same way two passes in a row
  • a PCR or ADR blocks the only workable fix
  • a test turns out weaker than the issue asked for (refactor asks before strengthening it)
  • they finish, with a short report of what they did and the commit hash

The board

The skills form a kanban board. Each skill is a station, and a piece of work moves left to right through them. Work starts as a GitHub issue, filed by either map-epic or new-issue, never both. From there the three code stations take it onto a branch.

The git flow

An issue gets its own branch, cut from main and named <issue-number>-<slug>. Each code station leaves its own commit on that branch, so you can read the history and see exactly what each station did. Nothing is pushed or merged by a skill. Opening the pull request and merging it back is your job.

architect-issue runs git checkout -b from whatever branch you are on. Run git checkout main && git pull before you start it, or the issue branch will grow out of the wrong place.

Two terms the diagram leans on:

  • Stub. A function with its final name, parameters and docstring, whose body only raises "not implemented". It pins down what the function looks like before anyone writes it.
  • Acceptance file. One test file, tests/test_acceptance.py, holding this issue's tests and nothing else. It is the finish line for implement. Refactor moves its tests into the normal test files and deletes it.

What a grilling round looks like

Most skills interview you before they write anything. The questions come in numbered rounds, and every question carries Claude's recommended answer. Here is one round from /new-issue users can export a chat as a PDF.

claude
> /new-issue users can export a chat as a PDF
⏺

❓ Q1 - What goes in the PDF?: A chat holds the messages, the sources the agents cited, and the final verdict. Which should the export include?

a) Only the messages, as they appear in the chat
b) The messages, plus the cited law sections and detaljplan pages under each answer
c) Only the verdict and its sources, without the conversation

➡️ b. Someone handing the PDF to a kommun needs to see where each claim comes from.

❓ Q2 - Empty chat: A brand new chat has no messages yet, so there is nothing to export. What should the user see?

➡️ Hide the export button until the chat has at least one answer.

> Q1 b, but put the verdict at the top as well. Q2 agree.
⏺

Settled. The PDF opens with the verdict, then the messages with their cited sources. Empty chats show no export button.

❓ Q3 - ...

Answer by number and keep it short. Pick an option by its letter, add a tweak if the option is close but not right, or say "agree" to take the recommendation. Disagreeing is fine and often the point. If every answer is "agree", you probably skipped the thinking the interview exists for.

The stations

Epic or single issue?

map-epic and new-issue both end in GitHub issues, but they never work on the same thing. map-epic owns every issue under an epic. new-issue refuses epic work and points you to map-epic. Pick one before you start.

Your workUse
Part of a goal that already has an (N) [epic] issue/map-epic N
A goal that needs several issues and has no epic yet, like "add geological data to the agents"/map-epic plus the goal. It files the epic first
One bug or one small feature that stands alone, like "the sidebar loses the active session after a reload"/new-issue
Standalone, but too big for one issue/new-issue. It offers to split it into sub-issues under a normal parent issue
Not sure it's worth doing at all/brainstorming. It ends by naming which of these to run

A quick test: if you can picture three or more issues that only make sense together, it's an epic. If it ships alone, it's a single issue.

map-epic

station 1GitHub only

Turns a big goal into an epic and splits it into issues. An epic is a large goal, like "the verdict covers ground conditions", that needs several issues to reach. Run it again later when earlier issues close, and it turns the vague leftovers into real issues.

New epic
Interviews you until the goal is one sentence describing what works when the epic is done. It checks the goal really needs several issues and isn't already covered by an open epic. Then it files the epic issue, (3) [epic] Geological data, and moves straight on to mapping.
It does
Asks questions across the whole epic and sorts every item into one of four piles. A task is ready to build. A research issue is a question someone must answer first. A prototype issue needs a quick mock-up first. Fog is something you know is coming but can't describe yet, so it stays as a note in the epic.
Stops for you
Before filing a new epic issue. Then "Publish this batch?" Then once per task issue, to review its text.
Leaves behind
Sub-issues titled (2.1) [feature] ..., linked to the epic, with "blocked by" links between them.
# new epic
/map-epic add geological data so the verdict covers ground conditions
# existing epic
/map-epic 2
# later, after some of epic 2's issues have closed
/map-epic 2
# pick from a list of epics
/map-epic

new-issue

beside the boardGitHub only

For one piece of work that no epic covers: a bug, a small feature. If it belongs to an epic, use map-epic instead.

It does
First asks "feature or bug?", then interviews you about what the user sees. It refuses to talk about files, function names or tests. That is architect's job.
Stops for you
When it suggests splitting into several issues, and before publishing each one.
Leaves behind
A GitHub issue with Goal, Expected behaviour, Out of scope, and a branch name.
/new-issue
/new-issue the chat sidebar loses the active session after a page reload

architect-issue

station 2red commit

Decides what the code will look like from the outside, then writes failing tests for it. You own this part. Every name and parameter gets agreed with you here.

It does
Reads the issue and the code around it, posts a "What I found" summary, then interviews you about each new function: name, parameters, return value, and what errors it raises. Then it creates the branch, writes the stubs and tests/test_acceptance.py, and runs the tests to check every one fails for the right reason.
Stops for you
After "What I found", so you can correct it. Then at the staged diff. Nothing is committed until you approve.
Leaves behind
Branch 42-<slug>, one commit Architect #42: ..., and sometimes a new ADR in docs/adr/ if you argued over a design choice.
# from an up-to-date main
/architect-issue 42
# at the diff gate
looks good, commit
# or, to fix something small
rename export_chat to export_session, keep the rest

If your objection is about the design itself, not a name, say so. It goes back to the interview rather than patching the code.

implement-issue

station 3green commit

Writes the code behind the stubs until the acceptance file passes. It may not rename anything or touch a test. Every other choice is its own, so it won't ask you about them.

It does
Reads the issue and the architect's diff, then loops: write code, run the acceptance file, read failures. It reports each pass as "pass 3: 2 of 6 still red".
Stops for you
Only when something is wrong that isn't its call: a test that contradicts the issue, a stub that can't do the job, or no progress after two passes.
Leaves behind
One commit Implement #42: ... and a comment on the issue listing the passing tests.
# on the issue branch
/implement-issue

refactor-issue

station 42 or 3 commits

The last station. Checks the tests actually prove what the issue asked for, runs the full test suite, cleans up the code against our project rules, and closes the issue.

It does
Checks each expected behaviour in the issue against the tests. Runs the whole suite and fixes old tests the issue made out of date. Cleans the code against docs/pcr/, docs/adr/ and its own code standards. Updates CONTEXT.md and README.md if the branch changed something they describe. Moves the acceptance tests into the normal test files.
Stops for you
If a test is weaker than the issue asked for. It asks before strengthening it.
Leaves behind
Refactor: ... and Tests #42: fold acceptance file, plus Fix #42: ... if implement broke something. The issue is closed. A report of tables lists what it changed.
# on the issue branch
/refactor-issue

After this, push the branch and open a PR into main. That step is yours.

Some issues get an autopilot label from new-issue or map-epic. The autopilot-issue skill it points at isn't in this repo yet, so run those issues through architect, implement and refactor like any other.

Side skills

These aren't stations. Use them whenever you need to think something through.

brainstorming

For a raw idea you aren't sure about. Claude tries hard to kill it, reshapes it every time it breaks, and ends with "killed" or "holds" plus which station should take it next.

/brainstorming cache retrieved detaljplan chunks per kommun so repeat questions are faster

grilling

The interview engine the other skills use. On its own it stress-tests any plan. This is the one skill that also starts from plain words.

/grilling my plan for splitting the orchestrator into two services
grill me on whether we should drop the access gate

pro-con

Weighs two or more options, tags each point by how much it matters, and commits to one.

/pro-con Mistral OCR vs running Tesseract ourselves for detaljplan PDFs

challenge-pcr

PCRs are project-wide rules in docs/pcr/, for example "all model calls go through llm.py". No other skill may change them. When one is in your way, this skill judges whether it should change. The default answer is no.

/challenge-pcr 0006 we want answers in Swedish for Swedish users

Full example

A small bug, from idea to merged PR. Everything you type is below.

# 1. file the issue
/new-issue the chat sidebar loses the active session after a page reload
#    answer the rounds, approve the preview. Issue #42 is filed.

# 2. red
git checkout main && git pull
/architect-issue 42
#    answer the rounds, review the diff, say "commit"

# 3. green, in a fresh session
/implement-issue

# 4. refactor, in a fresh session
/refactor-issue

# 5. ship
git push -u origin 42-sidebar-session-reload
gh pr create --base main
