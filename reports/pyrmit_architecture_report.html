Pyrmit: architecture, needs and workflows

October 25, 2026. How the project runs today, what it needs, where money is needed, and how a team of people and coding agents can share the same corpus, databases and budget. Current stack: GitHub, Linear, Neon, plus OpenRouter for the LLM and one development PC with a GPU. Sizes and timings were measured on that PC on October 25; prices come from the hosting report of October 9 (third-party trackers, to check before paying).
Summary
  • Today one PC does everything: the offline pipeline (crawl, OCR, indexing) and the app. Neon holds users and chats, OpenRouter the LLM. GitHub has the code, Linear the issues. CI runs only the frontend lint.
  • The data grew past a laptop: 1.9M chunks, a 7.4 GB corpus store and 194 GB of crawled PDFs, 5 to 10× the October 9 figures. It should live in object storage and travel as versioned corpus snapshots, built once on the GPU machine and pulled by everyone else.
  • Money goes to LLM tokens first (about $10 per 1,000 answers, $2–3 per benchmark round), then object storage (about $3 a month for the PDFs), a server (CPU, price to check) and optional GPU rental for peaks. Neon, GitHub and Linear stay on their current plans.
  • Pool what is expensive or slow: one corpus build shared as snapshots, one LLM account with a capped key per person, agent and environment, one GPU queue that runs at night, one Neon project with a branch per PR and worktree.
  • Two kinds of data, never mixed: mutable app state (Neon, branched per environment) and immutable corpus snapshots (files, pinned per environment, promoted after checks).
  • Worktrees: each gets its branch, its Neon branch and its ports, and all share one read-only data folder. Only one backend can hold the full store on the 8 GB GPU; the others run on the CPU or on the small corpus.
  • First steps cost nothing: backend tests in CI, Neon branches per PR, capped OpenRouter keys. Then snapshots on R2 and a staging server.

2. Target organisation

The draft below keeps four layers. Planning decides what is done, development does it (people and agents, in parallel), shared services are pooled across everyone, and environments run the result. The dollar badges mark where money is spent.

  • Planning: Linear holds every task, including those given to agents. The Linear–GitHub integration links branches and PRs to issues and moves their status, so a PR is always traceable to a decision.
  • Development: people work interactively in worktrees; long jobs (crawl, OCR, rebuild, re-embedding, paid benchmarks) never run on laptops but on the shared GPU box, at night; cloud agents take well-scoped issues and open PRs that a person reviews.
  • Shared services: one account each, split by keys, branches and folders rather than duplicated per person.
  • Environments: previews prove the code, staging proves the next corpus, production only changes through these two.

4. Pooling the needs

The expensive or slow things are built once and shared; the cheap things are split per person by keys, branches and folders, never by copying the whole stack.

  • Corpus snapshots replace "send the data folder": a rebuild costs GPU hours, a download costs minutes. Everyone (people, agents, CI, staging, prod) reads the same immutable files, so a bug report names a snapshot.
  • Capped keys: a runaway agent or benchmark can only spend its own cap (Windows keeps killed Python jobs alive: a "stopped" benchmark kept spending once). The product's keys stay separate from people's experiments.
  • One GPU queue: the 8 GB card holds either the app (6.5 GB) or a batch job, not both. Batch jobs are queued for the night, with the app stopped, as the night script already does.
  • Neon branches are copies on write: a branch per PR or worktree costs almost nothing and isolates schema changes and test data.

5. Databases and data versions

  • Never mix app state and corpus: the corpus is rebuilt from raw data at any time, the app state is not. Keeping the corpus out of Neon also keeps Neon in its free tier (1.9M chunks would take ~8–11 GB there).
  • A snapshot is a folder such as corpus-20261025-arctic-l-v2/ holding the store, the plan registry, check.json and a manifest of counts; CORPUS_DATA_DIR already selects one, as data/small does today.
  • Raw data is the source of truth for rebuilds: append-only in a bucket, so any snapshot can be rebuilt, and the PDF viewer and map tools read from it through a local cache.
  • Results stay in git: they are small, and the reports are generated from them.

6. Workflows

6.1 Code, for people and agents alike

6.2 Data, on the GPU box

  • Weekly: corpus.crawl --revisit (new PDF links on known pages, ~35k requests, about an hour); a full crawl (~166k requests, several hours) monthly or when the crawl rules change.
  • Nightly, while the OCR backlog lasts: OCR until a deadline, then the rebuild (extraction → filter → chunks → embeddings → store → plans → checks → replay), as the night script does; then publish snapshot N+1 to R2.
  • Release: staging switches to N+1; the coverage benchmark and, with a budget, the agent benchmarks run there; production switches when they hold. A failed check stops the release, not the night.

6.3 Evaluation

  • Every paid run has a label and runs on its own capped key; results (JSON) are committed and the reports are regenerated from them, so a number in a report always points to a file.
  • Free checks run on every snapshot (data checks, tool replay, coverage); paid benchmarks run when the prompts, the model or the corpus change in a way the free checks cannot judge.

  • One GPU backend per 8 GB card: the store and model take 6.5 GB. Measured with the GPU hidden on Oct 25: a search in one kommun takes 0.03–0.14 s on the CPU and in the statutes 0.03 s, but a search over the whole country 13–16 s (3.9 GB of vectors read per query). CPU worktrees should use the small corpus or questions that name a kommun.
  • Ports and stale processes: on Windows a stopped shell leaves its Python and Node children running; each worktree uses its own ports, and processes are checked and stopped before a restart.
  • Agents: one issue, one worktree, one branch, one Neon branch, one capped key. Long jobs (OCR, full crawls, re-embedding, paid benchmarks) are not run by agents: they are queued on the GPU box.
  • Shared data is read-only: only the night build writes a new snapshot folder, so worktrees never see a half-written store.
